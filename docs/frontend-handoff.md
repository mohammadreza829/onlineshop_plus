# تحویل بک‌اند به فاز فرانت

این سند قرارداد اتصال است، نه انتخاب فریمورک یا تایید انتشار production. نوع فرانت، روش نگهداری token، دامنه‌ها، SSR/SPA و design system باید پیش از پیاده‌سازی با صاحب پروژه تعیین شوند. هیچ فرانت جدیدی در این تحویل ساخته نشده است.

## مراجع قرارداد

- [OpenAPI ثابت](openapi-v1.yaml)، نسخهٔ زنده `/api/schema/` و Swagger `/api/docs/`.
- [API پایه و ورود](api-v1.md)، [variant/کوپن/نظر/علاقه‌مندی/پیگیری/staff](shop-features.md)، [جستجو/پیشنهاد/کش](backend-performance.md).
- تست `api.test_schema_snapshot` تغییر قرارداد را نسبت به فایل ثابت آشکار می‌کند. برای تغییر عمدی: `python manage.py spectacular --validate --fail-on-warn --file docs/openapi-v1.yaml` و سپس اجرای تست کامل.
- مسیر اصلی `/api/v1/` است؛ aliasهای `/orders/api/v1/` برای سازگاری هستند، نه توسعهٔ قابلیت تازه.

## شروع اتصال و احراز هویت

1. `GET client-options/`: واحد `TOMAN`، منطقه زمانی سرور، سقف تعداد هر خط/خطوط سبد، pagination و گزینه‌های استان با `value`/`label`. دادهٔ محرمانه یا تنظیم CORS برنمی‌گرداند. در حال حاضر فقط پنج استان مدل پشتیبانی می‌شوند؛ پوشش سراسر کشور فرض نشود.
2. برای session-auth: `GET csrf/` با حفظ cookie؛ مقدار JSON یعنی `csrf_token` را در `X-CSRFToken` درخواست‌های نوشتنی ارسال کنید. حتی با HttpOnly بودن cookie هم JSON قابل استفاده است. بعد از ورود/چرخش session دوباره bootstrap کنید. توکن CSRF جای احراز هویت نیست و Origin نامعتبر را مجاز نمی‌کند.
3. برای JWT: OTP request/verify و سپس `Authorization: Bearer ...`. access پنج دقیقه و refresh یک روز است؛ refresh می‌چرخد، پس هر دو مقدار جدید جایگزین شوند. logout فقط refresh داده‌شده را blacklist می‌کند؛ access تا انقضا معتبر می‌ماند. token در URL/log قرار نگیرد. راهکار ذخیره‌سازی نهایی هنوز انتخاب نشده است.
4. **سبد حتی با JWT مبتنی بر session cookie است**؛ از اولین افزودن تا checkout همان cookie باید حفظ شود. در fetch هم‌مبدا/اتصال مجاز cookie credentials را حفظ کنید؛ bearer به‌تنهایی سبد را بازیابی یا بین دستگاه‌ها sync نمی‌کند. هیچ CORS wildcard، cross-origin cookie یا BFF از پیش انتخاب نشده است.

## سبد و مبالغ

- `POST cart/` افزودنی است: product_id، quantity از ۱ تا ۱۰۰ و برای محصول دارای تنوع، variant_id.
- `PATCH cart/items/{product_id}/` **مقدار مطلق** را تعیین می‌کند: `{ "quantity": 3, "variant_id": 12 }`. برای بدون‌تنوع variant_id حذف شود. مقدار صفر حذف می‌کند و تکرار صفر بی‌خطر است؛ مقدار مثبت خط ناموجود را ایجاد نمی‌کند و 404 می‌دهد.
- پاسخ PATCH کل سبد تازه همراه `quantity_clamped` است. موجودی کمتر می‌تواند تعداد واقعی را کاهش دهد؛ UI همیشه تعداد و جمع پاسخ سرور را مبنا بگیرد. PATCH تکراری همان مقدار، افزودن دوباره نیست. قرارداد جدید فقط در مسیر canonical است؛ alias قدیمی PATCH را 405 می‌دهد.
- DELETE همان خط را حذف می‌کند؛ variant_id در query لازم است اگر خط تنوع دارد. خط محصول غیرفعال هم قابل حذف است.
- قیمت/تخفیف/ارسال/موجودی کلاینت قابل اعتماد نیست؛ checkout زیر قفل دوباره بررسی می‌کند. نگهداری خط در سبد رزرو موجودی نیست.
- مبالغ رشتهٔ decimal با تومان صحیح هستند؛ تبدیل ریال فقط مسئولیت adapter درگاه است. محاسبهٔ مالی با floating point مرورگر جایگزین سرور نشود. فیلتر/مرتب‌سازی قیمت کاتالوگ بر اساس قیمت پایه است، نه الزاماً مبلغ نهایی variant.
- تاریخ‌های API را با timezone/ISO تفسیر کنید؛ نمایش شمسی انتخاب UI است. مقدار `time_zone` از bootstrap خوانده شود.

## جریان خرید و بازیابی خطا

1. سبد → OTP/JWT یا session معتبر → آدرس خود کاربر → `POST orders/create/` با address_id و در صورت نیاز coupon_code.
2. سفارش و snapshot مبلغ/خطوط و reserved_until را از پاسخ بگیرید. ساخت سفارش رزرو است، نه اثبات پرداخت. checkout جدید ممکن است pending قبلی را جایگزین کند؛ این endpoint کلید idempotency عمومی ندارد. بعد از timeout مبهم POST را کورکورانه تکرار نکنید؛ ابتدا `GET orders/` و جزئیات سفارش را بررسی کنید.
3. `payment_api_url` endpoint **POST** است؛ آن را با احراز هویت صدا بزنید و سپس به `payment_url` در پاسخ درگاه بروید. لینک legacy به session و CSRF نیاز دارد؛ GET مستقیم endpoint شروع پرداخت مجاز نیست.
4. callback `/payment/verify/` ممکن است بدون session باشد. `Status=OK/NOK` مرورگر مدرک پرداخت نیست. وضعیت سفارش خود کاربر را مجدداً از API بخوانید؛ `is_paid` و status سرور مبنا هستند. پرداخت نامشخص ممکن است نیازمند reconcile باشد؛ با فاصله و سقف تلاش وضعیت سفارش را بررسی کنید، نه پرداخت اجباری یا checkout مجدد.
5. callback کاربر JWT-only سبد cookie را خودکار پاک نمی‌کند؛ فقط پس از تایید سفارش پرداخت‌شدهٔ خود کاربر `DELETE cart/` کنید. خطای دسترسی/شبکه را موفقیت پرداخت تلقی نکنید.
6. tracking/notifications فقط متعلق به کاربرند؛ staff endpoints برای مشتری 403 هستند. `needs_review` نیازمند بررسی عملیات است. لغو سفارش مالی اجرای بانکی refund نیست.

## قرارداد خطا و داده

- فهرست‌ها: count/next/previous/results و limit/offset (پیش‌فرض۲۰، سقف۱۰۰). از فرض array خام یا snapshot ثابت پرهیز کنید.
- 400: field errors، detail یا خطاهای لیستی؛ UI هر سه را مدیریت کند. 401: در صورت وجود refresh معتبر یک بار refresh و retry مجاز؛ حلقهٔ refresh ممنوع. refresh هم‌زمان در کلاینت serialize شود.
- 403: CSRF یا permission؛ 404: ناموجود یا غیرقابل دسترس؛ 405: روش نادرست؛ 429: رعایت Retry-After؛ 503 OTP: تحویل موفق پیامک/ورود را فرض نکنید.
- پاسخ‌های canonical و legacy API شامل `Cache-Control: private, no-store` هستند؛ service worker/CDN نباید دادهٔ سبد/حساب/پرداخت را shared-cache کند. کش داخلی توصیهٔ محصول فقط شناسه‌های عمومی را طبق TTL نگه می‌دارد.
- recommendation و review و coupon را مطابق قرارداد مرجع و پاسخ سرور نمایش دهید؛ نظر تاییدنشده/اطلاعات مالک دیگر عمومی نیست. اعلان فعلاً داخل حساب است، نه SMS وضعیت.

## تعریف آمادگی و باقی‌مانده

تست جریان خرید، CSRF، مالکیت، سبد، callback تکراری و پرداخت نامشخص با transport پیامک و درگاه mock اجرا می‌شود؛ نه پرداخت یا ارسال واقعی. فایل قرارداد و راهنمای اتصال برای شروع گفت‌وگوی فرانت آماده‌اند. این به معنی تضمین نبود باگ نیست.

[گیت‌های انتشار](backend-release-checklist.md) همچنان جداگانه لازم‌اند: کلیدها/چرخش secret، SMS واقعی، درگاه و settlement واقعی، TLS و تنظیم دامنه/proxy، استقرار مقصد، تست بار/soak/outage هدف، بازیابی backup مقصد و ارزیابی امنیت. پذیرش مرورگری و دسترس‌پذیری بعد از انتخاب و ساخت فرانت انجام می‌شود. تغییر پوشش استان، account-synced cart یا refund بانکی پروژهٔ مستقل‌اند و این تحویل آن‌ها را پیاده‌سازی‌شده معرفی نمی‌کند.
